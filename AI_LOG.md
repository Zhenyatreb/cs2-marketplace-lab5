# Журнал взаємодії із ШІ для лабораторної роботи № 5

## 1. Початковий промпт

> Проаналізуй наявний навчальний сайт CS2 Market, створений на HTML, CSS і JavaScript. Запропонуй найпростішу зрозумілу архітектуру повноцінного навчального вебзастосунку з клієнтською частиною, сервером Node.js/Express, PostgreSQL та REST API. Потрібно реалізувати CRUD для каталогу скінів: перегляд усіх товарів, перегляд одного товару, додавання, редагування та видалення. Збережи наявний темний дизайн і зображення, не додавай реальну авторизацію Steam, платежі або складні функції. Додай валідацію даних, обробку помилок, захист секретів через `.env`, базові заходи безпеки та інструкцію локального запуску й розгортання.

## 2. Промпт для перевірки згенерованого рішення

> Перевір структуру проєкту, REST-маршрути, SQL-запити та клієнтські Fetch-запити. Переконайся, що всі дані перевіряються на сервері, SQL-запити параметризовані, секрети не потрапляють до GitHub, CRUD повертає правильні HTTP-статуси, а клієнт показує зрозумілі повідомлення про помилки. Не додавай функції, які не потрібні для лабораторної. Склади список перевірок для браузера.

## 3. Короткий опис відповіді ШІ

ШІ запропонував використати Node.js та Express для серверної частини, PostgreSQL для зберігання товарів, а Fetch API та async/await — для отримання даних у браузері. Для каталогу запропоновано CRUD-маршрути GET, POST, PUT і DELETE.

## 4. Перевірка та внесені рішення

- Обрано одну таблицю `skins`, оскільки для навчального каталогу цього достатньо.
- Збережено попередній інтерфейс CS2 Market та наявні зображення.
- Додано серверну перевірку назви, типу зброї, ціни, стану, Float Value та шляху зображення.
- Для SQL використано параметризовані запити, щоб не вставляти введений користувачем текст безпосередньо в SQL-команди.
- Секрети винесено в `.env`; файл додано до `.gitignore`.
- Операції додавання, редагування та видалення захищено кодом адміністратора, що зберігається на сервері у змінній середовища.
- Реальний Steam-вхід та платежі не реалізовувалися, оскільки вони не потрібні для перевірки CRUD і REST API в цій лабораторній.

## 5. Що потрібно перевірити вручну

Після налаштування Neon та локального запуску потрібно перевірити GET, POST, PUT і DELETE, негативні випадки валідації, роботу сайту на різних екранах, вкладку Console та журнал Render після розгортання. До звіту вносити лише фактично отримані результати.
